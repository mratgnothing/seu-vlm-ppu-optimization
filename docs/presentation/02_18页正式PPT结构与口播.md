### P01 面向 PPU 的 Qwen3.5-2B 高效推理优化

画面：主标题、团队信息、副标题。Qwen/PPU 是主视觉，手机/EEG 仅作次要提示。

口播：我们的核心任务是指定模型在指定 PPU 上的推理优化。完成基础实验后，我们进一步探索了手机部署与脑机协同交互。

不要在封面写“已实现脑电控制手机”或“PPU INT4 全模型加速”。

### P02 任务要求与评测指标

画面文案：固定模型与硬件；Accuracy；首 token 延迟 TTFT；解码吞吐；系统级实现与复现。

主视觉：指标定义与约束，保留硬件、模型、接口三个条件。无最新书面通知时不写评分权重。

口播：优化必须在同一模型和同一评测入口下成立。Accuracy 检查答案，TTFT 测第一个输出 token，吞吐测解码阶段效率，工程实现还需要稳定和可复现。

来源：正式项目 `README_ORGANIZER.md`、`docs/rules-and-boundaries.md`。两者有历史评分公式差异，不能任取一个当当前最终公式。

### P03 固定模型与真实推理基线

画面文案：Qwen3.5-2B 固定 revision；本地 GPU 与 PPU 分阶段验证；PPU 参数全部驻留；公开双语数据与分块审计。

主视觉：简洁工程时间线。本地 4050 全量数字可放讲者备注，不与 PPU 最终数字混排。

口播：我们先建立真实 Transformers 基线，核对模型版本、数据和评测口径，再在 PPU 上完成图片、混合主干和生成的真实闭环。全部参数驻留目标设备，没有 CPU 或磁盘 offload。

来源：`docs/current-status.md`、`docs/work-summary/README.md`。

### P04 Qwen3.5 的混合结构与推理阶段

画面文案：24 层主干，18 GDN + 6 Attention；GDN 递推状态；Attention KV；Prefill 与 Decode 分工。

主视觉：可沿用旧 P05 v2 的结构思路，正式绘制时核对六组 3+1。不要把整个模型画成纯线性注意力。

口播：Qwen3.5 混合了递推状态与全注意力两类路径。Prefill 处理输入，Decode 每生成一个 token 都重复投影和状态更新，这给模型专用融合提供了机会。

来源：`docs/qwen35-kernel-targets.md`。

### P05 真实 PPU 的运行时瓶颈

画面文案：16-token profile；37,293 次 launch；8,832 次分配操作；大量小算子与主机提交。

主视觉：有范围标注的真实事件统计。没有原始 trace 截图时用日志统计，不生成假的 profiler 时间线。

口播：本地 GPU 上矩阵运算是主要热点，但真实 PPU 的 profile 显示大量短 kernel、临时张量和提交开销。自写 GEMV 没有超过成熟实现，因此我们把重点转向融合模型特有算子和减少运行时边界。

来源：`docs/work-summary/README.md`。self CPU/PPU time 可以放备注，但不要当作墙钟延迟柱状图。

### P06 量化路线与当前平台约束

画面文案：权重与状态量化分开评估；格式需要 kernel 支持；计入转换与调度成本；PPU 全模型量化尚待验证。

主视觉：量化对象、运行时支持、模型级评测的关系。主讲应明确“正式结果使用 BF16”。

口播：我们评估了量化格式与关键投影尺寸。当前环境中，官方 weight-only 依赖和部分形状支持存在约束，量化成本也需要整模测量。所以正式采用可验证的 BF16 融合与运行时优化，PPU 全模型 INT8/INT4 的收益仍需专门验收。

来源：`docs/work-summary/README.md` 的 A16W8/A16W4 记录、`docs/qwen35-kernel-targets.md`、赛事规则。

### P07 模型专用 Decode 融合

画面文案：GDN 状态更新；causal-conv；norm/gate；Q/K norm + partial RoPE。可在示意下写“减少重复提交与中间结果”。

主视觉：一条代表性 GDN 小算子链与融合后实现，其他核只列名字。旧 P07 v2 可供参考。

口播：我们把每步重复的 GDN 状态更新、卷积和归一化等过程做成模型专用融合核，减少中间张量和调度。首阶段五类融合把 CN20 吞吐从约 49.7 提高到约 94.9 token/s。它有明确生成漂移记录，因此继续进入任务回归。

来源：`docs/work-summary/README.md`，融合实验记录。这里的阶段数值用于解释演进，最终数字仍以 P12 为准。

### P08 MLP 布局与提交边界

画面文案：gate/up packed storage；共享输入；一个入口组织完整 MLP；scratch 复用。

主视觉：权重布局与 gate/up、SwiGLU、down 的执行关系。注明“一个 C++ 入口可能包含多个设备 kernel”。

口播：我们把共享输入的 gate/up 投影组织成 packed storage，再用一个扩展入口提交完整 MLP 并复用中间缓冲。它减少上层调用，不要求常驻第二套同样的权重。中英文完整集上，该增量分别约为 11.25% 和 10.93%。

来源：`docs/work-summary/README.md` 的单入口 packed-MLP 部分。增量相对前一栈，不能与其他阶段相加。

### P09 GDN 投影与运行时优化

画面文案：grouped 提交；raw stream 查询；保守 b/a 合并；双语增量回归。

主视觉：GDN 投影提交前后或减少每 token 重复调用的示意，展示 b/a 合并保留 qkv/z。

口播：后期继续减少 GDN 投影和 stream 查询的重复开销。我们选择仅合并 b/a 两个小投影，保留主要投影形状。这项增量在双语 4029 题中保持全文、答案和 token 数一致。

来源：`docs/work-summary/README.md`、双语 b/a-GEMV 完整集结果 JSON。

### P10 首 Token 路径优化

画面文案：Prefill 多行 norm/residual；首 token 独立分析；最终 TTFT 降低 4.79%。

主视觉：输入处理与逐 token decode 的阶段关系。不要使用未经测量的等比例整任务时间条。

口播：解码收益会在很多 token 上重复，首 token 还包含输入与视觉路径。因此我们单独分析 prefill，让已有归一化和残差融合覆盖多行。最终 ABBA 的 TTFT 降低 4.79%，范围仍是公开 CN20。

来源：`results/ppu-first-token-prefill-row-fusions-20260901.json`、最终 ABBA JSON。不要把原记录的 1.04859x 速度比直接写成耗时降低 4.86%。

### P11 精度门禁与优化取舍

画面文案：模块检查；固定长度配对；真实任务；双语完整集。代表案例“single-GEMV 英文少 1 题，正式关闭”。

主视觉：候选通过/拒绝的门禁流程，主图只保留一个数值案例。

口播：局部速度不能决定是否进入正式配置。更激进的 single-GEMV 虽然更快，却在英文完整集少答对一题，所以我们保留保守方案。模块更快但整模回退的路线也明确止损。

来源：工作总结与 single-GEMV 双语决策记录。

### P12 最终 PPU 实测结果

画面核心：**49.22 与 133.62 token/s，2.715 倍**。次要指标：TTFT 120.059 与 114.313 ms，降低 4.79%；Accuracy 85% 与 85%。

主视觉：原生可编辑吞吐对照图与小表。脚注建议直接写：

> PPU-ZW810E · Qwen3.5-2B · BF16 · batch 1 · 公开 CN20 · 四进程 ABBA，每臂两次；答案一致，总栈全文一致性未验证。

若字号不足，删除次要文案，不删除样本范围。token 数 15/20 一致写在讲者备注，并准备回答。

口播：同一 PPU、固定中文公开 20 题和四个独立进程的 ABBA 对照中，最终栈吞吐是 eager 的 2.71484 倍，TTFT 降低 4.79%，四次准确率均为 85%，答案全部一致。这证明当前样本范围的端到端推理收益，不能外推到全量或私有测试。

来源：`results/ppu-final-best-vs-eager-cn20-abba-20260901.json`。
